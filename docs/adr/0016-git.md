# ADR-0016: Git: the sealed runtime's git through a host, with credentials through Git's own helper protocol

**Status:** Accepted · 2026-11-23 · Phase 7 W1 ([PHASE_7_PLAN.md](../phases/PHASE_7_PLAN.md) W1, which assigns these choices to W1, with numbers) · the engine and the credentials' channel chosen by the agent from W1's measurements · **still the owner's** (PHASE_7_PLAN §10): what Git does with folders from shared storage (item 2), which credentials Phase 7 builds (item 3), and the Git budgets (item 4)

## Context
- **ROADMAP's Phase 7:** init, status, stage, commit, diff and branches on the sealed Git; clone, pull and push with credentials kept in the Keystore; a large repository without a freeze; the strategy for folders from shared storage decided.
- **What can run:** the sealed runtime has carried git 2.56.1 since Phase 4, with libcurl 8.23.0, the certificates and openssh 10.6p2, and programs come only from the APK ([SECURITY.md](../SECURITY.md) §2). Until W1, only `git --version` had been run (`RuntimeCommandsTest` a): nothing had used git's own programs, its templates or a network.
- **Planned since Phase 0:** credentials in an Android Keystore-backed store (ARCHITECTURE §4), handed to Git per operation through askpass or a credential helper, never in files on the PATH or in a child's environment (SECURITY §2, §4).

## Options
- **The engine:**
  - the runtime's `git`, run through the launcher like every other program;
  - JGit, in the app's JVM: TECH_STACK set it aside in Phase 0, since the spec prefers the existing binary and JGit adds JVM weight and behaviour that differs from Git's.
- **The credentials' channel:**
  - `GIT_ASKPASS`: a program that answers one prompt string at a time, without knowing the host's protocol or path;
  - Git's credential helper protocol: `get` with the protocol, host and path, then `store` after a success or `erase` after a refusal. It tells the app exactly which host asks, and whether a credential worked;
  - the helper's transport to the app: a script in the runtime's bash over two FIFOs the host makes for an operation, or a small native helper next to the launcher.

## Measured
`GitTest` (W1) runs the runtime's git through the launcher's command mode, over the APK's own payload, on the five runtime legs (API 26, 27, 28, 34 and 36) and on Test Lab's Pixel 8a with Android 14, in a profile build: 7 of 7 tests on every target in phase gate 45250655049 (evidence `02a0eab8` and `e5c38722`).

**The first gate found two faults in the runtime itself** (45244989137, cancelled before Test Lab ran; evidence `cf3c68b5`). On all five legs:
- `git init` and `git clone` failed: "cannot stat template '/data/data/com.termux/files/usr/share/git-core/templates/description'";
- HTTPS failed within 13 to 65 ms with "remote helper 'https' aborted session", whether or not `http.sslCAInfo` named the certificates.

Git's compiled-in paths are Termux's official prefix. CodeForge's preload translates what a program executes, opens and lists there, but not what it stats, and git finds its templates and its helper programs (`git-remote-https`, `git-http-backend`) by `stat`. The terminal's git had the same faults. Since fc9df410, `RuntimeEnvironment` names both in the prefix for every command and terminal: `GIT_EXEC_PATH` (`libexec/git-core`) and `GIT_TEMPLATE_DIR` (`share/git-core/templates`). The second gate passed on every target.

- **The untracked status of 10,000 files wrote 160,000 bytes,** within the launcher's 1 MiB of kept output. W2's host streams a status, whatever its size.
- **SSH works as a client.** `ssh-keygen` made an Ed25519 key with a passphrase and read it back, and GitHub's server refused the unknown key after the full handshake, on every target. A clone over SSH from the runtime's own `sshd` on 127.0.0.1 failed: sshd called the app's user invalid before authentication. The server is a test fixture, not something CodeForge ships, so this proves nothing about SSH remotes.
- **The credential helper's FIFOs worked on Android 8 to 16:** each `get` answered in the same operation, `store` after success, `erase` after a refusal, and nothing in an argument, the environment or a file.

## Decision
- **The engine is the runtime's git,** run through a host in Kotlin (W2) like every other program: in its own process group, ended with its tree, under the sessions' limits. JGit stays set aside.
- **Credentials reach Git only through Git's own credential helper protocol,** on the command line of the operation that needs them: an empty `credential.helper` first, so no other helper runs, then CodeForge's. The host answers `get` for exactly the host that asks, and learns from `store` and `erase` whether a credential worked.
- **The helper's transport is a script in the runtime's bash over two FIFOs** the host makes for each operation, in app-private storage with mode 600, as W1 measured. No native helper is needed.
- **Git's paths are named in the prefix** (`GIT_EXEC_PATH`, `GIT_TEMPLATE_DIR`), for the panel's git and the terminal's alike.
- **HTTPS uses the payload's certificates as they are:** no `http.sslCAInfo` is needed.

## Consequences
- **The terminal's `git init`, `git clone` and HTTPS remotes work since fc9df410.** They had failed since Phase 4, unnoticed, because nothing had run them.
- **A large repository is fast enough to budget:** on the Pixel 8a, `status` of 10,000 files took 134 ms at the 95th percentile and of 50,000 files 262 ms, through the launcher. The app's own path adds the host, the parse and the panel. PHASE_7_PLAN §10, item 4 proposes the budgets from these numbers.
- **SSH is feasible as a client** (PHASE_7_PLAN §10, item 3): keys, the handshake and the host key check work on every target. An authenticated clone over SSH needs a key a host accepts, so W3 proves it, or the owner's phone checklist does.
- **Housekeeping runs in the foreground** (`gc.autoDetach=false`; W1 used `gc.auto=0`): the launcher ends whatever a command leaves running, which would cut a detached `gc` short.
