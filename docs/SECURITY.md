# Security

**Status:** Living document · Principles locked Phase 0; controls land with their phases

CodeForge executes user code, shell commands, and (later) third-party extensions. Security is designed in from the start — and described **honestly**: we state what is isolated and what is not.

---

## 1. Trust boundaries (what is actually isolated)

| Boundary | Real? | Mechanism |
|---|---|---|
| App ↔ rest of OS | ✅ | Android app sandbox (UID, SELinux); no root, no special permissions for core features |
| App ↔ shared storage | ✅ | SAF: user-consented trees only, persistable URI grants, revocable; as built in Phase 3, §4.1 |
| WebView renderer ↔ app | ✅ (partial) | Android WebView renderer process isolation; our bridge is the only doorway, validated |
| User code ↔ app data | ❌ **NOT isolated** | Child processes run as the app UID: they can read app-private files. **We never claim otherwise** (spec §7). Mitigations below reduce blast radius, not eliminate it |
| Extension code ↔ app | ❌ same UID | Permission system is a policy layer + interpreter scoping, not an OS sandbox (Phase 8 doc will repeat this) |

UI copy and docs must say "runs locally in CodeForge's sandbox" — never "securely sandboxed" about user code.

## 2. Runtime execution controls (Phase 4+)

The design, with what is built so far. §2.1 is the review of the exec boundary as built in Phase 4 W4. **Since W7** the install goes through the vendored kernel's own entry point, `SealedInstaller.install`, which verifies every file against the payload's manifest while writing it. It carries CodeForge's one recorded patch, which makes it run below API 33 (native/PROVENANCE.md, *Patches*); from W5 to W7 the host repeated the kernel's steps itself.

- **Exec model:** only APK-backed executables run (sealed invariant; `ExecAudit` = 0 enforced at startup; non-zero → degraded mode + user-visible report). User *scripts* are interpreted by shipped interpreters — never `execve`'d from data. **Built:** the audit since Phase 4 W3; one-shot commands since W4 (§2.1).
- **No downloaded executables, ever** (Play policy + W^X): packages/packs arrive only via Play Feature Delivery or a new APK. npm/pip installing **native** addons is a known tension: Phase 5 documents that node-gyp/pip source builds require the build-tools pack and produce data-dir binaries that **cannot exec** at target 36 — such installs are detected and reported with guidance (pure-JS/wheel alternatives), not silently broken. This limitation is surfaced in Runtime Diagnostics.
- **Resource limits:** `ulimit`-style rlimits on child processes where bionic supports (CPU time, file size, nproc); OOM-score adjustments; session count cap (default 8); output flood coalescing. Measured, not assumed. **Built in W4:** no core files (`RLIMIT_CORE` 0), a time limit on every command and a cap on each output stream (§2.1). **Built in Phase 5 W2:** the cap of 8 terminals, a bounded thread pool, and output batching with credit flow control (§2.2). **Not yet:** the rlimits and the OOM score (Phase 5 W5).
- **Process hygiene:** process-group kill on session close; foreground service notification with "kill all"; no background execution without a visible session. **Built in W4:** every command ends with its whole process tree (§2.1). **Built in Phase 5 W2:** every terminal session ends with its whole tree, and *End all* ends them all (§2.2). **Not yet:** the foreground service (Phase 5 W5).
- **Environment:** secrets are not injected into child env by default; Git credentials supplied per-invocation via askpass/credential helper, never `PATH`-visible files. **Built in W4:** the environment is built from nothing (§2.1). Git credentials come with Phase 7.

### 2.1 The exec boundary as built: the security review (Phase 4 W4)

ROADMAP's review at a new boundary, like §4.1's for shared storage: each threat with its mitigation and its proof. The code is in `app/android/app/src/main/kotlin/dev/codeforge/app/runtime/` and the launcher in `native/runtime-core/src/main/jni/codeforge-spawn.c`. It is CodeForge's own; t1's environment and runner are not vendored ([native/PROVENANCE.md](../native/PROVENANCE.md)).

**The model.** Dart asks for one command through the Pigeon API (`RuntimeApi.exec`): a program, its arguments, a folder, a time limit and an output cap. The host answers only while the runtime is ready or degraded, never during an install. `CommandRunner` takes the program from the runtime's `bin` by name and starts it through the launcher, `libcodeforge-spawn.so`, which ships in the APK beside the payload's programs. The launcher's environment holds `LD_PRELOAD` with CodeForge's `harness-exec`, so its own `execv` goes through the preload, which translates the official Termux `#!` line of a script to the shipped interpreter. The answer is typed: an exit code or a signal, stdout and stderr apart (each capped, with its full byte count), the duration, and a failure kind (`not_ready`, `bad_request`, `not_found`, `cannot_execute`, `timed_out`, `ended`, `signaled` or `launch_failed`). In W4 the app runs only its own commands: the tool probes (*Check the tools*) and the tests. Nothing the user writes runs before Phase 5.

**Still true:** commands run as the app's UID. They can read and write everything the app can (§1). Everything below narrows what they reach by default and makes sure they end; none of it is an OS sandbox.

| # | Threat | Mitigation | Proof |
|---|---|---|---|
| E1 | **A binary from the app's data runs** | The program must be a name in the runtime's `bin`: no `/`, no NUL, and no path from Dart. Every program there is a link into the APK's library folder, and the audit at every start finds any that is not (W3). The preload is CodeForge's `harness-exec` alone. t1 also preloads Termux's `termux-exec`, which can run an ELF file from the app's storage through the system linker, so it is left out | JVM `CommandRunnerTest` (*onlyProgramsInTheRuntimesBinRun*), `RuntimeEnvironmentTest`; on the emulator `RuntimeCommandsTest` (b) and the W3 audit |
| E2 | **The app's variables or secrets reach a command** | The environment is cleared, then built from nothing (`RuntimeEnvironment`). From the app's process only Android's system locations pass, at most six of them (`ANDROID_ROOT`, `ANDROID_DATA`, `ANDROID_ART_ROOT`, `ANDROID_I18N_ROOT`, `ANDROID_TZDATA_ROOT`, `ANDROID_RUNTIME_ROOT`). The rest is the runtime's: `PATH` (its `bin`, then `/system/bin`), `HOME`, `PWD`, `TMPDIR`, the four XDG folders, `LANG` and `LC_ALL` (`C.UTF-8`), `TERM` (`dumb`), `SHELL`, `PREFIX`, the three paths `harness-exec` translates to, `LD_LIBRARY_PATH`, `LD_PRELOAD`, the certificates, and `PYTHONHOME`, `NODE_PATH`, `GEM_HOME`, `RUBYLIB` and `PERL5LIB` for what the payload carries | JVM `RuntimeEnvironmentTest` (*nothingComesFromTheAppsProcessButAndroidsLocations*), `CommandRunnerTest` (*itRunsInTheHomeWithTheRuntimesVariablesOnly*); on the emulator `RuntimeCommandsTest` (b): in phase gate 43837693816, `env` saw exactly the 29 variables built, five of them Android's (API 36 has no `ANDROID_RUNTIME_ROOT`), and not the canary the test adds to the app's variables |
| E3 | **A command works in the user's project by default, or in a folder chosen from outside** | `HOME`, `TMPDIR` and the XDG folders are in the runtime's root (t1's layout), never in a project. A command runs in the runtime's home unless it names a folder, and a named folder must lie inside the runtime's home or its workspace once symbolic links are resolved. **Since W6** one command also runs in a project's folder: the search host's ripgrep, which reads its globs from where it runs. The extra root is the projects' folder, given by the search host alone (`CommandRunner.stream`'s `extraRoots`); `RuntimeApi.exec` cannot ask for it | JVM `RuntimeEnvironmentTest` (*homeTmpdirAndXdgLiveInTheRuntimesRoot*), `CommandRunnerTest` (*aFolderInsideTheWorkspaceIsAllowedAndOutsideIsNot*) |
| E4 | **A process outlives its command:** a child left running, a process that left the group, a double-forked daemon | The launcher leads a session and a process group of its own and is a child subreaper, so every orphan of the tree comes back to it. When the command exits, ends or is stopped, the launcher finds its group and every descendant through `/proc`, sends each `SIGTERM` and `SIGCONT`, then `SIGKILL` after the grace period (1 s), for up to 3 s, and reaps them. If the launcher itself outlives that by a margin (grace + 4 s), the registry kills its whole group (`kill(-group, SIGKILL)`) and the process | `runtime/tests/test-spawn.py` (16; each of five mutants of the launcher fails some of them); JVM `CommandRunnerTest` (real processes on CI's machine: a child left running, a time limit, a command ignoring `SIGTERM`, ending every session); on the emulator `RuntimeCommandsTest` (e, f): in phase gate 43837693816, a tree of five `sleep`s (two in the group, a subshell's orphan, one that `setsid` moved to a session of its own, and the one bash waited for) ended in 100 ms, with nothing left in its group or out of it and the app's processes as before. A time limit and a command that exited left nothing either |
| E5 | **A command runs forever, or floods the app with output** | Every command has a time limit: 60 s unless asked, between 100 ms and 10 minutes. `SessionRegistry` enforces it, then ends the whole tree (E4). stdout and stderr are read apart, each kept up to its cap (256 KiB unless asked, between 1 KiB and 1 MiB) and counted past it. stdin is closed at once, so a command that reads it gets end-of-file | JVM `CommandRunnerTest` (*outputPastTheLimitIsCountedNotKept*, *aCommandPastItsTimeLimitIsEndedWithEverythingItStarted*); on the emulator `RuntimeCommandsTest` (d): a 1 KiB cap kept 1,024 of 300,000 bytes and counted them all; `sleep 30` with a 500 ms limit came back `timed_out` after 510 ms |
| E6 | **A crash leaves a core file in the app's storage** | The launcher sets `RLIMIT_CORE` to 0 for itself and everything it starts. A crash comes back as `signaled`, with its signal | `test-spawn.py` (*a crash writes no core file*); JVM `CommandRunnerTest` (*aCrashIsReportedAsTheSignalThatEndedIt*) |
| E7 | **A command runs while the prefix is replaced** | Commands hold a read lock on the prefix, and an install takes the write lock. Before an install the registry ends every session and refuses new ones until it is done. Commands are taken only while the runtime is ready or degraded | JVM `RuntimeHubTest` (*commandsAndProbesWaitForAReadyRuntime*, *aFailedInstallTakesNoCommands*), `CommandRunnerTest` (*endingEverySessionEndsTheirTreesAndRefusesNewOnes*) |
| E8 | **A request that Kotlin should not trust:** a path for a program, a NUL byte, a folder outside, a limit out of range | Kotlin checks the request again and never trusts Dart: the program is a name (not empty, `.` or `..`, no `/` or NUL), no argument holds a NUL, the folder passes E3's check, and each limit is brought into its range | JVM `CommandRunnerTest` (*onlyProgramsInTheRuntimesBinRun*, *aFolderInsideTheWorkspaceIsAllowedAndOutsideIsNot*). The limits' ranges have no test of their own |

**Signals and limits as built.** The launcher resets every signal to its default and unblocks all of them, so a command doesn't inherit the app's ignored or blocked signals. Its exit status is the command's, `128 + n` when signal `n` ended the command, `126` or `127` when the program cannot be run or is missing, and `125` for the launcher's own failure. Its status file (`files/coding-harness/codeforge/sessions/`) records the pid, the group, whether it became a subreaper, how the command ended, and how many processes it ended and left.

**Search (Phase 4 W6).** A project's search is one command that Kotlin builds itself (`RipgrepSearch.kt`): the program is `rg`, the query goes after `--regexp`, so a leading `-` stays a pattern, and the globs after `--glob`. None of it passes through a shell. ripgrep only reads, from the project's folder, which the search host checks lies in `<filesDir>/workspaces` once links are resolved. It follows no links (ripgrep's default; nothing asks it to), reads no configuration file and no ignore file above the project, and its output is read line by line with each line capped (8 MiB) and the results capped (10,000 lines). A folder from shared storage is scanned through the storage broker's operations on its grant (`DocumentOps`), so §4.1's rules hold unchanged: the grant is checked, names come from the provider's own listings, reads stop at 10 MiB, and every call can be cancelled. Search adds no access.

**Not yet, before Phase 5 runs code the user wrote** (Phase 5's plan takes these on, measured on the devices):
- CPU-time, file-size and process-count limits, and the OOM-score adjustment, each measured with bionic and Android's cgroups before it is set (W5);
- the foreground service with "kill all", and what becomes of the processes when Android ends the app (W5).

**Built in Phase 5 W2** (§2.2): the session cap (8 terminals), a bounded pool for the commands' threads (16), and output coalescing with credit flow control for the terminal.

**Evidence:** the JVM tests run in every CI run (CI 43835601536: `kotlin_tests=101 failures=0 errors=0 skipped=0`, so `CommandRunnerTest` started real processes, as it must on CI); `test-spawn.py` runs in CI's runtime job; `RuntimeCommandsTest` runs in every phase gate's runtime group. Phase gate 43837693816 passed it (`runtime_instrumented=pass OK (12 tests)`, with `RuntimeInstallTest`). Its figures are in that run's `app/ci-results/gate/runtime_logcat.txt` (`RUNTIME_GATE commands_*`): the runner took the classes in name order, and `RuntimeInstallTest` started the shared report afresh, so `runtime.txt` lost them. Later gates copy the class's own report (`runtime_commands_report.txt`).

### 2.2 Terminal sessions as built (Phase 5 W2)

W2 adds interactive sessions at the same boundary (TERMINAL_ARCHITECTURE §1; the PTY's design in ADR-0014). Dart asks `TerminalApi.start` for a session: a project's folder name or none, a program's name or none (the shell), arguments, environment overrides and a size. The host checks the request (`Terminals`), reserves a place, and starts the launcher in terminal mode, which runs the program on a pseudo-terminal and relays between it and the app. W5 completes this section with the limits, the foreground service and the app's death (G5).

**Still true:** a session runs as the app's UID, like a command (§2.1), and the user types into it what they like. Everything below narrows what a session reaches by default, bounds what it costs the app, and makes sure it ends; none of it is an OS sandbox.

| # | Threat | Mitigation | Proof |
|---|---|---|---|
| T1 | **A terminal runs a binary from the app's data, or a shell that is not the runtime's** | E1 holds: the program is a name in the runtime's `bin`, and the default is its bash. Without bash nothing starts (`not_found`); there is no fallback to `/system/bin/sh`. Inside a session the exec rule is the same as for a command: the APK's programs, and scripts through the shipped interpreters | JVM `TerminalSessionTest` (*aProgramIsANameInTheRuntimesBin*, *withoutBashNoSessionStartsAndNothingElseIsTried*) |
| T2 | **The app's variables reach a terminal, or an override breaks the runtime** | The environment is E2's, built from nothing, plus four terminal variables (`TERM`, `COLORTERM`, `SHELL`, `TERMINFO`). Overrides may add variables, never replace the runtime's own, Android's locations, or any `LD_*` or `TERMUX_*`. A name must be an identifier and a value holds no NUL; at most 64 overrides of 32 K characters together | JVM `TerminalSessionTest` (*overridesCannotReplaceTheRuntimesOwnVariables*, *aTerminalsVariablesDifferFromACommandsInFour*; *theSessionsEnvironmentIsTheTerminalsAndTheRcFileIsCodeForges*, with the canary of the app's variables absent) |
| T3 | **A terminal starts in a folder chosen from outside** | E3 widens with care: the runtime's home, or a project's folder named by its folder name (no `/`, not `.` or `..`), which the host resolves in `<filesDir>/workspaces` and accepts only if, links resolved, it lies directly in it. A path from Dart is never taken. A folder from shared storage runs in its copy (W4, ADR-0013) | JVM `TerminalSessionTest` (*aSessionStartsInTheHomeOrInAProjectTheHostNames*: a link out, `..`, a path, a missing project) |
| T4 | **A terminal's processes outlive it:** jobs in groups of their own, an orphan, a daemon | The launcher is the tree's subreaper and stays outside the shell's session. Ending a session hangs the terminal up: `SIGHUP`, `SIGTERM` and `SIGCONT` to every descendant, `SIGKILL` after the grace period. The registry's last resort also kills every group of the shell's session, which `/proc` lists | `runtime/tests/test-pty.py` (19, CI's runtime job; nine mutants of the launcher each fail some); JVM `TerminalSessionTest` (*endEndsTheShellAndEverythingItStarted*, *theNinthSessionIsRefusedAndEndAllEndsThemAll*); on the emulators `TerminalSessionTest` (g): in phase gates 44461809588 and 44475934378, End all of an interactive shell with three jobs (one of them a subshell's orphan) and of a script with two children took 102 to 114 ms on API 26 to 36, leaving no process of either tree and the app's processes as before |
| T5 | **Sessions or threads without bound** | At most 8 terminal sessions. The place is reserved before anything starts, so the ninth is refused without a process. Commands, probes and starts share a bounded pool of 16 threads; a session has two threads of its own | JVM `TerminalSessionTest` (*theNinthSessionIsRefusedAndEndAllEndsThemAll*); on the emulators `TerminalSessionTest` (f), `terminal_ninth=too_many` |
| T6 | **A flood exhausts the app's memory or freezes it** | The ring buffer keeps 1 MiB. A view gets batches at most every 16 ms and holds at most the window (256 KiB) unacknowledged; then the reader stops, the launcher stops reading the terminal, and the program blocks in the kernel. Input is queued up to 1 MiB and refused past it (`input_full`) | JVM `TerminalSessionTest` (*aFloodArrivesWholeAndTheCreditBoundsWhatIsHeld*: 10 MiB whole, the reader stopped at the window without credit; *anEndFromTheRegistryReachesASessionWhoseViewStoppedAcknowledging*); on the emulators `TerminalSessionTest` (e): in phase gates 44461809588 and 44475934378, 10 MiB whole in 0.67 to 0.88 s, never more than the 256 KiB window unacknowledged, and the Java heap at most 2,155 KiB larger (the test allows 32 MiB; the figure includes garbage not yet collected) |
| T7 | **A terminal runs while the prefix is replaced** | A session starts under the prefix's read lock, and only while the runtime is ready or degraded. An install ends every session and refuses new ones, takes the write lock, then ends again any session that started meanwhile | JVM `TerminalSessionTest` (*anInstallsEndAllRefusesNewSessionsUntilReopened*), `RuntimeHubTest` (*terminalsWaitForAReadyRuntimeToo*) |
| T8 | **Input from the app desynchronises the relay, or a size is abused** | Input and sizes are typed frames, in order on one pipe. A frame of an unknown type, or a size of the wrong length, ends the session (`lost`, stop cause `protocol`). Sizes are brought into range (Kotlin's 1 to 999, the launcher's 1 to 9999) | `test-pty.py` (unknown frames, sizes); JVM `TerminalSessionTest` (*sttySizeFollowsAResize*, with sizes out of range) |

**Evidence:** test-pty.py in CI 44445690182 (19 tests); the JVM tests in the bootstrap run 44451456079 (`kotlin_tests=161`, 23 more than before: `TerminalSessionTest`'s 22 and one in `RuntimeHubTest`); the instrumented class in phase gates 44461809588 and 44475934378, on API 26 to 36 (the first gate, 44454605348, found End all's race on API 26), and on Test Lab's arm64 phone, a Google Pixel 8a with Android 14, in CI 44482754814 (End all 112 ms, the flood whole in 1.04 s).

## 3. WebView & bridge hardening (Phase 2+)

- **One self-contained page** (decided in Phase 2; it replaces the original `WebViewAssetLoader` plan). `webview_flutter_android` 4.14.1 exposes no request interception, so `WebViewAssetLoader` is unreachable through the plugin. The editor page is therefore a single document with its script, style and font inline, loaded with `loadHtmlString` under the base URL `https://appassets.androidplatform.net/`, and it makes no network or file requests. The build records the page's SHA-256 in `manifest.json`; the host verifies the asset against it before loading.
- CSP: `default-src 'none'; script-src 'sha256-<build hash>'; style-src 'unsafe-inline'; font-src data:; base-uri 'none'; form-action 'none'`. The hash pins the one inline script, so a modified script does not run, and every other fetch (`connect-src`, `img-src`, frames) falls back to `'none'`. `editor/tool/verify_bundle.mjs` checks the pin against the built page in CI. At the Phase 2 exit (CI 42678576228) the page is 768.4 KiB (291,951 B gzipped), its SHA-256 is `84431233cb8721838888d4a7230c9c5f074c30b7f69e9604bb7c0aa6f67caa8a`, and the CSP pins `sha256-csqXDdzzvB25mLR2mBYrAmqOOjLWRYZ7xGw6yMzoWRc=`. Both hashes change whenever the page does; `app/ci-results/editor/{build,verify}.txt` records them on every bootstrap run.
- WebView settings (`app/lib/services/editor/webview_editor_surface.dart`): `setAllowFileAccess(false)`, `setAllowContentAccess(false)`, geolocation off, media playback only after a user gesture, page zoom off, text zoom pinned at 100 % (the host sends a font size that already includes the user's text scale), JavaScript dialogs refused, remote debugging only in debug builds (`enableDebugging(kDebugMode)`). JavaScript runs only in this one page. The page uses no web storage: editor state lives in Dart. Mixed content and cookies never come into play, because the page makes no requests.
- **The page is verified before it runs:** the host hashes `editor.html` and compares it with the SHA-256 in `manifest.json` (`app/lib/services/editor/editor_page.dart`); a mismatch, a malformed manifest or a different protocol version fails closed. The pane then shows the reason and a retry, and never loads the page.
- **Benchmark pages (Phase 2 W3, non-release builds only):** Settings → Developer → Editor benchmark loads the CodeMirror and Monaco benchmark pages from `assets/editor_bench/`. They are verified against their `manifest.json` hashes the same way (`app/lib/services/editor/bench/bench_pages.dart`) and run in a WebView with the same settings (`bench_surface.dart`). Their `CodeForgeBench` channel only reports measurements to the screen and reaches no file, document or protocol, so it has no rate limit. The developer screens are compiled out of release builds (`kReleaseMode`). The phase gate builds the pages after its release APK, so release builds carry none.
- **One bridge object, one method** (the `CodeForgeBridge` JavaScript channel, `postMessage(String)`); JSON envelope schema-validated on both sides (type allowlist per direction, version check, unknown fields rejected, size cap 32 Mi characters because whole-document messages must fit the largest supported file, 10 MiB (larger files are refused before they are read, W7), host-side token-bucket rate limit: bursts of 240, 120 messages/s, excess dropped and logged); the protocol carries no file paths at all (documents are opaque ids; file access stays in Dart, where W4 confines it to workspace roots); every failure typed + logged; no reflection, no generic "eval" or "exec" message types (the editor protocol's `cmd.exec` runs only a named command from a fixed allowlist, such as undo or indent).
- **Every navigation request is refused** (`onNavigationRequest` → prevent, and logged), the asset origin included: the page never navigates, and only the app's own `loadHtmlString` loads it. No download listener is installed, so nothing can be downloaded.
- **Renderer crashes:** `webview_flutter_android` 4.14.1 exposes no `onRenderProcessGone`, so if the WebView renderer dies, Android ends the app process (the platform default for an unhandled renderer crash). Unsaved text survives that through the edit journal (W5), which brings it back on the next start: phase gate 42386742421 crashed the renderer of a running app holding unsaved text, and the next start restored all of it, still unsaved, with the cursor. A page reload short of a crash is recovered in-app: the host reopens every document from its shadow copy.

## 4. Data protection

| Data | Control |
|---|---|
| Git tokens / SSH keys (Ph. 7) | Android Keystore-backed encryption (AES-GCM, key never leaves Keystore); encrypted blobs in app-private storage; never logged, never in child env by default; SSH via openssh with key files chmod 600 in runtime home, passphrase prompt UI |
| Settings/workspace DB | app-private, and the app itself syncs nothing. **Android's backup is the user's choice, off by default** ([ADR-0012](adr/0012-backup-opt-in.md), Phase 3 W1). Until then it was on by Android's default (found in Phase 2 W8). Settings → Privacy → *Back up with Android* states what Android copies, where, and on what terms: the projects, their unsaved text and the settings, to the user's Google Drive, at most 25 MB, about daily, end-to-end encrypted on Android 9 and later with a screen lock. A backup agent decides on every pass, reading the switch from a host-owned file (`codeforge.backup.xml`), because Android runs it without the app's startup:<br>• **on:** `files/workspaces`, `files/codeforge.sqlite` and its `-wal`, `FlutterSharedPreferences.xml` and the switch's file, exactly the include lists of both rules files;<br>• **off:** nothing, so Android keeps no backup (it declines an empty one);<br>• **off after a backup with everything:** the switch's file alone, which replaces that backup.<br>Never in a backup: the logs (`no_backup/`), caches, the WebView's data, and folders opened from shared storage. A device-to-device transfer follows the same switch and the same files. **Limit:** turning it off takes effect at Android's next backup, which an app cannot start. Evidence: `BackupPolicyTest` (JVM, the rules files against the policy), and the gate's `backup` group, which uses `bmgr` with the local transport (the default declined, then on → reinstall restores, then off → reinstall gives a fresh app). Backup/export as an explicit user action: Phase 10 |
| Logs | bounded ring buffer; redaction at logger (tokens, key paths, env values matching secret patterns; since Phase 3 W1 also `content://` URIs, cut to their authority), so every sink gets redacted records. **On disk since Phase 3 W1:** `no_backup/logs/codeforge.log` and the previous `codeforge.1.log`, at most 1 MiB each, in the folder Android never backs up, whatever the backup switch says. Errors reach the disk at once (flushed and synced), so a crash's last records survive it. Leaving the device requires a user action: Settings → About → Recent logs → *Copy* takes the newest 256 KiB, and *Save* (W4) writes all of them to a file the user picks (§4.1). In debug and profile builds, Settings → Developer → *Log viewer* (W6) shows this session's records and copies what it shows. All of these carry records that were redacted when they were logged |
| Temp files | app-private tmp; cleaned on session end + startup sweep. A save's temp file (`.<name>.cf-tmp`, W4) sits beside its target and is deleted when the save fails; one left by a crash is hidden from listings and replaced by the next save of that file |
| Workspace files | **projects:** one app-private folder each, `<filesDir>/workspaces/<name>` (the demo's `demo` since Phase 2 W4, the others since Phase 3 W3); **folders from shared storage:** through the storage broker only (§4.1). In a project, every path is checked as text (relative, no `.` or `..`, no control or reserved characters), then on disk: the deepest existing ancestor, symbolic links resolved, must lie inside the canonical root, so neither `..` nor a link can reach outside it. Writes are atomic (temp file, flush, rename): an interrupted save leaves the old file. Files that are not UTF-8 text are refused, so they are never rewritten. **Permission bits (Phase 3 W1):** a save keeps the old file's mode. The temporary file takes it before the rename, through libc's `chmod` over `dart:ffi`, so a script stays executable and a private file stays private. If `chmod` fails, the save goes on and a warning is logged |
| Network | core features fully offline; network used only for: git remotes (user-initiated), pack delivery (Play), extension install (Phase 8, user-initiated), docs links. No telemetry, no analytics. **Until Phase 4's end** the release build asked for no permissions at all, so it had no internet access. **From Phase 5 W1** (the owner's decision, 2026-11-18) it asks for INTERNET, so the userland's tools reach the network when the user runs them (`npm install`, `pip install`, `git clone`/`push`, `curl`); the app's own code still connects nowhere, and the editor and terminal pages load only bundled assets (§3). Android grants it to the app's uid, so every process the app starts may open sockets: a command reaches whatever address it names, as it would on a computer. What leaves the phone is what the user's command sends, where the command sends it: a user-initiated transfer (docs/store/data-safety.md). CI's *Release manifest* gate fails the build on any other permission (Phase 4 W7, widened in Phase 5 W1). Code a command downloads (an npm package, a pip wheel) runs inside the same sandbox as everything the user runs (§2); a native module that npm or pip fetches is the user's download, not CodeForge's (ADR-0005; PHASE_5_PLAN §9) |

### 4.1 Folders from shared storage: the storage scoping review (Phase 3 W2)

ROADMAP's gate for Phase 3. Written before the storage broker's code, and kept as the record of what it must hold. Each threat names its mitigation and the test that proves it. **Done at Phase 3's exit (W7):** every mitigation below is built, and every proof runs in CI (the JVM and Dart tests) or in every phase gate (the `folders` group); PHASE_3_REPORT.md cites the runs.

**The model.** A folder workspace is a tree the user picked in Android's folder picker (`ACTION_OPEN_DOCUMENT_TREE`). The app keeps the grant with `takePersistableUriPermission` (read and write) and asks for no storage permission. Only `StorageBroker.kt` touches `content://`: Dart calls it through one typed Pigeon API (`StorageApi`) with a tree URI and a workspace-relative path, and gets names, sizes, times and bytes back. The tree URI is an opaque token to Dart; document ids and document URIs never leave Kotlin.

| # | Threat | Mitigation | Proof |
|---|---|---|---|
| S1 | **A path that escapes the folder:** `..`, an absolute path, an empty segment, a name holding `/` | Paths are checked twice. Dart checks them as text (`core/files/workspace_path.dart`). Kotlin checks every segment again (`StoragePaths`) and never trusts Dart: not empty, not `.` or `..`, no `/`, NUL or control character, at most 255 UTF-8 bytes. The broker then walks from the granted folder's root, name by name, through the provider's own listings. It never builds a document id from text. | JVM `StoragePathsTest`, `DocumentOpsTest`; Dart `saf_file_service_test`; gate `folders`: paths with `..` sent straight to the broker are refused |
| S2 | **A document outside the tree reached another way:** a provider's own id, a symbolic link | Every call uses a tree-based document URI (`buildDocumentUriUsingTree`). Android's `DocumentsProvider` checks each one against the tree (`enforceTree`, `isChildDocument`); the device's storage provider compares canonical paths, so a link out of the tree fails. The broker also refuses any tree URI that is not among the app's persisted grants. | gate `folders`: a folder beside the granted one is refused |
| S3 | **A hostile or slow provider:** wrong or huge sizes, endless streams, slow or hanging calls, odd names | The 10 MiB cap is checked from the listed size before a file is opened, and every read stops one byte past the cap whatever size the provider claimed. Every call has a time limit: Kotlin cancels it through a `CancellationSignal` and answers `timeout`, and Dart's own limit sits just above. Calls run on a small pool of background threads, never on Android's main thread. A listing keeps at most 50,000 entries and skips names that break S1's rules or repeat. Folder copies stop at 64 levels. | JVM `CappedReadTest` (an endless stream, a size that lies, the time running out), `DocumentOpsTest` (the listing and copy limits); Dart `saf_file_service_test` (too large; the broker's `timeout` code) |
| S4 | **A grant that went stale:** the folder deleted or moved, the grant released or revoked, the storage removed | The broker tells three states apart. A tree with no persisted grant, or a `SecurityException`, is *access lost*; a root document that is gone is *missing*. The workspace shows that state and never crashes. A cached document id that fails is dropped, and the path is resolved again from the root. | Dart `workspace_switch_test`; gate `folders`: a deleted folder shows as missing, a released grant as access lost |
| S5 | **A URI reaching the WebView or the logs** | Tree URIs stay in the services and application layers. The editor page gets document text and opaque ids only: protocol v1 has no field for a path or a URI. A folder workspace's id is a SHA-256 hash of its URI. The URI itself is kept only in the app's private storage: in the shell envelope for the open folder (since W2), and in the app database's recents (`workspaces.location`, since W3), which Home needs to check and reopen each folder. The logger cuts any `content://` URI to its authority (Phase 3 W1), and the broker's Kotlin side logs no URIs. | Dart `logger_test` (W1); `saf_file_service_test`: workspace ids hold no URI |
| S6 | **Another app writing during our write; saves that cannot be atomic** | DocumentsContract cannot replace a file by renaming over it, so a save first compares the file's stamp (modified time and size, or a SHA-256 when the provider reports no time) and stops with *changed on disk*. The bytes then go in place with mode `"wt"`, which truncates (plain `"w"` can leave old bytes behind a shorter write). The stamp is read back afterwards, and its size must match. Until then the document stays unsaved, with its text in the journal: a failed or interrupted save never marks it saved. | JVM `DocumentOpsTest` (a stamp that changed, with and without a modified time; a write that leaves old bytes behind); Dart `saf_file_service_test` and `workspace_switch_test` (a changed stamp, a failed write: the tab stays unsaved); gate `folders`: shorter text over longer, checked with `sha256sum` |
| S7 | **Broad storage access** | No storage permission. The picker is the only way in, one folder at a time; Android 11 and later refuse the storage root, `Download` and `Android/`. | the merged manifest, checked by CI after every debug build since W6 (`tool/ci/check_manifest.py`: no storage permission, no legacy storage, ADR-0012's backup attributes) |

**Saving a copy (Phase 3 W4).** About → Recent logs → *Save* goes through the same broker: `saveDocument` opens Android's create-document picker (`ACTION_CREATE_DOCUMENT`), writes the bytes Dart sent to the one new file the user made there, and answers its display name. The app takes no persistable grant, so the file is the user's, written once; no URI comes back to Dart. What it writes is the log files' text, which is redacted as it is logged (secret-looking fields, `content://` URIs).

**Limits.** Android caps how many grants an app keeps. Since W3 the app gives a grant back when its folder leaves the recents (*Remove from recents*), when a reconnect points the entry at another folder (the old place's grant), and when a folder picked for a reconnect is turned down. The broker logs how many grants it keeps after each take and release (`workspace_switch_test` and `home_launcher_test` check the releases). Providers other than the device's shared storage are best effort: the rules above apply to them, and the gate tests the device's own.

## 5. Extension security model (Phase 8 preview)

Manifest-declared permissions (`workspace.read`, `workspace.write`, `terminal.spawn`, `network`, `theme`, `snippets`); install-time grant dialog; extensions run in a scoped JS interpreter (QuickJS evaluated in Phase 8) with **only** bridged APIs, no raw filesystem/process access; themes/snippets are declarative (no code). Failure isolation: extension crash ≠ IDE crash. Full spec: EXTENSION_API.md (written in Phase 8).

## 6. Supply chain

- Bootstrap + `.deb` pins with SHA-256 (t1 pattern); payload manifest verified while writing; build scripts unit-tested.
- Dependencies: lockfiles committed; license screening at intake; CI `npm ci`/locked pub; no install scripts from unreviewed packages (`npm ci --ignore-scripts` where feasible).
- Release signing: keystore outside repo (env/`keystore.properties` git-ignored), fails closed; Play App Signing for the Play track; GitHub artifacts signed with the same upload key, hashes published in release notes.
- CI secrets: least-privilege `GITHUB_TOKEN` (contents:read default; write only where a job publishes); no secrets in PR runs from forks.
- **As built in Phase 4:**
  - **The runtime's inputs** are pinned with their SHA-256 (runtime/pins.json), and a missing or changed package fails the build closed (W2).
  - **t1's vendored code** is checked file by file against t1's commit on every push; the one change beyond the package name is a recorded patch (native/PROVENANCE.md, W7).
  - **The licences:** the editor page's npm packages must carry a licence from a permissive allowlist, and every pub package, dev tools included, fails the build on GPL, AGPL, SSPL or an unknown licence. Since W7, THIRD_PARTY_NOTICES.md's lists are written from the resolved dependencies and checked on every push, the userland's included, and CI fails if a userland package has no licence named.

## 7. Vulnerability handling

Security issues: private report via GitHub security advisories (enabled Phase 1). Severity triage ≤ 72 h; patch releases out-of-band; CHANGELOG notes without exploit detail until users can update.
