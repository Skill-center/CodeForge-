# Security

**Status:** Living document · Principles locked Phase 0; controls land with their phases

CodeForge executes user code, shell commands, and (later) third-party extensions. Security is designed in from the start — and described **honestly**: we state what is isolated and what is not.

---

## 1. Trust boundaries (what is actually isolated)

| Boundary | Real? | Mechanism |
|---|---|---|
| App ↔ rest of OS | ✅ | Android app sandbox (UID, SELinux); no root, no special permissions for core features |
| App ↔ shared storage | ✅ | SAF: user-consented trees only, persistable URI grants, revocable |
| WebView renderer ↔ app | ✅ (partial) | Android WebView renderer process isolation; our bridge is the only doorway, validated |
| User code ↔ app data | ❌ **NOT isolated** | Child processes run as the app UID: they can read app-private files. **We never claim otherwise** (spec §7). Mitigations below reduce blast radius, not eliminate it |
| Extension code ↔ app | ❌ same UID | Permission system is a policy layer + interpreter scoping, not an OS sandbox (Phase 8 doc will repeat this) |

UI copy and docs must say "runs locally in CodeForge's sandbox" — never "securely sandboxed" about user code.

## 2. Runtime execution controls (Phase 4+)

- **Exec model:** only APK-backed executables run (sealed invariant; `ExecAudit` = 0 enforced at startup; non-zero → degraded mode + user-visible report). User *scripts* are interpreted by shipped interpreters — never `execve`'d from data.
- **No downloaded executables, ever** (Play policy + W^X): packages/packs arrive only via Play Feature Delivery or a new APK. npm/pip installing **native** addons is a known tension: Phase 5 documents that node-gyp/pip source builds require the build-tools pack and produce data-dir binaries that **cannot exec** at target 36 — such installs are detected and reported with guidance (pure-JS/wheel alternatives), not silently broken. This limitation is surfaced in Runtime Diagnostics.
- **Resource limits:** `ulimit`-style rlimits on child processes where bionic supports (CPU time, file size, nproc); OOM-score adjustments; session count cap (default 8); output flood coalescing. Measured, not assumed.
- **Process hygiene:** process-group kill on session close; foreground service notification with "kill all"; no background execution without a visible session.
- **Environment:** secrets are not injected into child env by default; Git credentials supplied per-invocation via askpass/credential helper, never `PATH`-visible files.

## 3. WebView & bridge hardening (Phase 2+)

- **One self-contained page** (decided in Phase 2; it replaces the original `WebViewAssetLoader` plan). `webview_flutter_android` 4.14.1 exposes no request interception, so `WebViewAssetLoader` is unreachable through the plugin. The editor page is therefore a single document with its script, style and font inline, loaded with `loadHtmlString` under the base URL `https://appassets.androidplatform.net/`, and it makes no network or file requests. The build records the page's SHA-256 in `manifest.json`; the host verifies the asset against it before loading.
- CSP: `default-src 'none'; script-src 'sha256-<build hash>'; style-src 'unsafe-inline'; font-src data:; base-uri 'none'; form-action 'none'`. The hash pins the one inline script, so a modified script does not run, and every other fetch (`connect-src`, `img-src`, frames) falls back to `'none'`. `editor/tool/verify_bundle.mjs` checks the pin against the built page in CI. At the Phase 2 exit (CI 42678576228) the page is 768.4 KiB (291,951 B gzipped), its SHA-256 is `84431233cb8721838888d4a7230c9c5f074c30b7f69e9604bb7c0aa6f67caa8a`, and the CSP pins `sha256-csqXDdzzvB25mLR2mBYrAmqOOjLWRYZ7xGw6yMzoWRc=`. Both hashes change whenever the page does; `app/ci-results/editor/{build,verify}.txt` records them on every bootstrap run.
- WebView settings (`app/lib/services/editor/webview_editor_surface.dart`): `setAllowFileAccess(false)`, `setAllowContentAccess(false)`, geolocation off, media playback only after a user gesture, page zoom off, text zoom pinned at 100 % (the host sends a font size that already includes the user's text scale), JavaScript dialogs refused, remote debugging only in debug builds (`enableDebugging(kDebugMode)`). JavaScript runs only in this one page. The page uses no web storage: editor state lives in Dart. Mixed content and cookies never come into play, because the page makes no requests.
- **The page is verified before it runs:** the host hashes `editor.html` and compares it with the SHA-256 in `manifest.json` (`app/lib/services/editor/editor_page.dart`); a mismatch, a malformed manifest or a different protocol version fails closed. The pane then shows the reason and a retry, and never loads the page.
- **Benchmark pages (Phase 2 W3, non-release builds only):** Settings → Developer → Editor benchmark loads the CodeMirror and Monaco benchmark pages from `assets/editor_bench/`. They are verified against their `manifest.json` hashes the same way (`app/lib/services/editor/bench/bench_pages.dart`) and run in a WebView with the same settings (`bench_surface.dart`). Their `CodeForgeBench` channel only reports measurements to the screen and reaches no file, document or protocol, so it has no rate limit. The developer screens are compiled out of release builds (`kReleaseMode`). The phase gate builds the pages after its release APK, so release builds carry none.
- **One bridge object, one method** (the `CodeForgeBridge` JavaScript channel, `postMessage(String)`); JSON envelope schema-validated on both sides (type allowlist per direction, version check, unknown fields rejected, size cap 32 Mi characters because whole-document messages must fit the largest supported file, 10 MiB (larger files are refused before they are read, W7), host-side token-bucket rate limit: bursts of 240, 120 messages/s, excess dropped and logged); the protocol carries no file paths at all (documents are opaque ids; file access stays in Dart, where W4 confines it to workspace roots); every failure typed + logged; no reflection, no generic "eval" or "exec" message types (the editor protocol's `cmd.exec` runs only a named command from a fixed allowlist, such as undo or indent).
- **Every navigation request is refused** (`onNavigationRequest` → prevent, and logged), the asset origin included: the page never navigates, and only the app's own `loadHtmlString` loads it. No download listener is installed, so nothing can be downloaded.
- **Renderer crashes:** `webview_flutter_android` 4.14.1 exposes no `onRenderProcessGone`, so if the WebView renderer dies, Android ends the app process (the platform default for an unhandled renderer crash). Unsaved text survives that through the edit journal (W5), which brings it back on the next start: phase gate 42386742421 crashed the renderer of a running app holding unsaved text, and the next start restored all of it, still unsaved, with the cursor. A page reload short of a crash is recovered in-app: the host reopens every document from its shadow copy.

## 4. Data protection

| Data | Control |
|---|---|
| Git tokens / SSH keys (Ph. 7) | Android Keystore-backed encryption (AES-GCM, key never leaves Keystore); encrypted blobs in app-private storage; never logged, never in child env by default; SSH via openssh with key files chmod 600 in runtime home, passphrase prompt UI |
| Settings/workspace DB | app-private, and the app itself syncs nothing. **Android's backup is the user's choice, off by default** ([ADR-0012](adr/0012-backup-opt-in.md), Phase 3 W1). Until then it was on by Android's default (found in Phase 2 W8). Settings → Privacy → *Back up with Android* states what Android copies, where, and on what terms: the projects, their unsaved text and the settings, to the user's Google Drive, at most 25 MB, about daily, end-to-end encrypted on Android 9 and later with a screen lock. A backup agent decides on every pass, reading the switch from a host-owned file (`codeforge.backup.xml`), because Android runs it without the app's startup:<br>• **on:** `files/workspaces`, `files/codeforge.sqlite` and its `-wal`, `FlutterSharedPreferences.xml` and the switch's file, exactly the include lists of both rules files;<br>• **off:** nothing, so Android keeps no backup (it declines an empty one);<br>• **off after a backup with everything:** the switch's file alone, which replaces that backup.<br>Never in a backup: the logs (`no_backup/`), caches, the WebView's data, and folders opened from shared storage. A device-to-device transfer follows the same switch and the same files. **Limit:** turning it off takes effect at Android's next backup, which an app cannot start. Evidence: `BackupPolicyTest` (JVM, the rules files against the policy), and the gate's `backup` group, which uses `bmgr` with the local transport (the default declined, then on → reinstall restores, then off → reinstall gives a fresh app). Backup/export as an explicit user action: Phase 10 |
| Logs | bounded ring buffer; redaction at logger (tokens, key paths, env values matching secret patterns; since Phase 3 W1 also `content://` URIs, cut to their authority), so every sink gets redacted records. **On disk since Phase 3 W1:** `no_backup/logs/codeforge.log` and the previous `codeforge.1.log`, at most 1 MiB each, in the folder Android never backs up, whatever the backup switch says. Errors reach the disk at once (flushed and synced), so a crash's last records survive it. Leaving the device requires a user action: Settings → About → *Copy* takes the newest 256 KiB |
| Temp files | app-private tmp; cleaned on session end + startup sweep. A save's temp file (`.<name>.cf-tmp`, W4) sits beside its target and is deleted when the save fails; one left by a crash is hidden from listings and replaced by the next save of that file |
| Workspace files (Phase 2) | one app-private folder, `<filesDir>/workspaces/demo` (W4). Every path is checked as text (relative, no `.` or `..`, no control or reserved characters), then on disk: the deepest existing ancestor, symbolic links resolved, must lie inside the canonical root, so neither `..` nor a link can reach outside it. Writes are atomic (temp file, flush, rename): an interrupted save leaves the old file. Files that are not UTF-8 text are refused, so they are never rewritten. **Permission bits (Phase 3 W1):** a save keeps the old file's mode. The temporary file takes it before the rename, through libc's `chmod` over `dart:ffi`, so a script stays executable and a private file stays private. If `chmod` fails, the save goes on and a warning is logged |
| Network | core features fully offline; network used only for: git remotes (user-initiated), pack delivery (Play), extension install (Phase 8, user-initiated), docs links. No telemetry, no analytics |

### 4.1 Folders from shared storage: the storage scoping review (Phase 3 W2)

ROADMAP's gate for Phase 3. Written before the storage broker's code, and kept as the record of what it must hold. Each threat names its mitigation and the test that proves it.

**The model.** A folder workspace is a tree the user picked in Android's folder picker (`ACTION_OPEN_DOCUMENT_TREE`). The app keeps the grant with `takePersistableUriPermission` (read and write) and asks for no storage permission. Only `StorageBroker.kt` touches `content://`: Dart calls it through one typed Pigeon API (`StorageApi`) with a tree URI and a workspace-relative path, and gets names, sizes, times and bytes back. The tree URI is an opaque token to Dart; document ids and document URIs never leave Kotlin.

| # | Threat | Mitigation | Proof |
|---|---|---|---|
| S1 | **A path that escapes the folder:** `..`, an absolute path, an empty segment, a name holding `/` | Paths are checked twice. Dart checks them as text (`core/files/workspace_path.dart`). Kotlin checks every segment again (`StoragePaths`) and never trusts Dart: not empty, not `.` or `..`, no `/`, NUL or control character, at most 255 UTF-8 bytes. The broker then walks from the granted folder's root, name by name, through the provider's own listings. It never builds a document id from text. | JVM `StoragePathsTest`, `DocumentOpsTest`; Dart `saf_file_service_test`; gate `folders`: paths with `..` sent straight to the broker are refused |
| S2 | **A document outside the tree reached another way:** a provider's own id, a symbolic link | Every call uses a tree-based document URI (`buildDocumentUriUsingTree`). Android's `DocumentsProvider` checks each one against the tree (`enforceTree`, `isChildDocument`); the device's storage provider compares canonical paths, so a link out of the tree fails. The broker also refuses any tree URI that is not among the app's persisted grants. | gate `folders`: a folder beside the granted one is refused |
| S3 | **A hostile or slow provider:** wrong or huge sizes, endless streams, slow or hanging calls, odd names | The 10 MiB cap is checked from the listed size before a file is opened, and every read stops one byte past the cap whatever size the provider claimed. Every call has a time limit: Kotlin cancels it through a `CancellationSignal` and answers `timeout`, and Dart's own limit sits just above. Calls run on a small pool of background threads, never on Android's main thread. A listing keeps at most 50,000 entries and skips names that break S1's rules or repeat. Folder copies stop at 64 levels. | JVM `CappedReadTest` (an endless stream, a size that lies, the time running out), `DocumentOpsTest` (the listing and copy limits); Dart `saf_file_service_test` (too large; the broker's `timeout` code) |
| S4 | **A grant that went stale:** the folder deleted or moved, the grant released or revoked, the storage removed | The broker tells three states apart. A tree with no persisted grant, or a `SecurityException`, is *access lost*; a root document that is gone is *missing*. The workspace shows that state and never crashes. A cached document id that fails is dropped, and the path is resolved again from the root. | Dart `workspace_switch_test`; gate `folders`: a deleted folder shows as missing, a released grant as access lost |
| S5 | **A URI reaching the WebView or the logs** | Tree URIs stay in the services and application layers. The editor page gets document text and opaque ids only: protocol v1 has no field for a path or a URI. A folder workspace's id is a SHA-256 hash of its URI. The URI itself is kept only in the app's private storage: in the shell envelope for the open folder (since W2), and in the app database's recents (`workspaces.location`, since W3), which Home needs to check and reopen each folder. The logger cuts any `content://` URI to its authority (Phase 3 W1), and the broker's Kotlin side logs no URIs. | Dart `logger_test` (W1); `saf_file_service_test`: workspace ids hold no URI |
| S6 | **Another app writing during our write; saves that cannot be atomic** | DocumentsContract cannot replace a file by renaming over it, so a save first compares the file's stamp (modified time and size, or a SHA-256 when the provider reports no time) and stops with *changed on disk*. The bytes then go in place with mode `"wt"`, which truncates (plain `"w"` can leave old bytes behind a shorter write). The stamp is read back afterwards, and its size must match. Until then the document stays unsaved, with its text in the journal: a failed or interrupted save never marks it saved. | JVM `DocumentOpsTest` (a stamp that changed, with and without a modified time; a write that leaves old bytes behind); Dart `saf_file_service_test` and `workspace_switch_test` (a changed stamp, a failed write: the tab stays unsaved); gate `folders`: shorter text over longer, checked with `sha256sum` |
| S7 | **Broad storage access** | No storage permission. The picker is the only way in, one folder at a time; Android 11 and later refuse the storage root, `Download` and `Android/`. | the merged manifest (W6 adds a CI check) |

**Saving a copy (Phase 3 W4).** About → Recent logs → *Save* goes through the same broker: `saveDocument` opens Android's create-document picker (`ACTION_CREATE_DOCUMENT`), writes the bytes Dart sent to the one new file the user made there, and answers its display name. The app takes no persistable grant, so the file is the user's, written once; no URI comes back to Dart. What it writes is the log files' text, which is redacted as it is logged (secret-looking fields, `content://` URIs).

**Limits.** Android caps how many grants an app keeps. Since W3 the app gives a grant back when its folder leaves the recents (*Remove from recents*), when a reconnect points the entry at another folder (the old place's grant), and when a folder picked for a reconnect is turned down. The broker logs how many grants it keeps after each take and release (`workspace_switch_test` and `home_launcher_test` check the releases). Providers other than the device's shared storage are best effort: the rules above apply to them, and the gate tests the device's own.

## 5. Extension security model (Phase 8 preview)

Manifest-declared permissions (`workspace.read`, `workspace.write`, `terminal.spawn`, `network`, `theme`, `snippets`); install-time grant dialog; extensions run in a scoped JS interpreter (QuickJS evaluated in Phase 8) with **only** bridged APIs, no raw filesystem/process access; themes/snippets are declarative (no code). Failure isolation: extension crash ≠ IDE crash. Full spec: EXTENSION_API.md (written in Phase 8).

## 6. Supply chain

- Bootstrap + `.deb` pins with SHA-256 (t1 pattern); payload manifest verified while writing; build scripts unit-tested.
- Dependencies: lockfiles committed; license screening at intake; CI `npm ci`/locked pub; no install scripts from unreviewed packages (`npm ci --ignore-scripts` where feasible).
- Release signing: keystore outside repo (env/`keystore.properties` git-ignored), fails closed; Play App Signing for the Play track; GitHub artifacts signed with the same upload key, hashes published in release notes.
- CI secrets: least-privilege `GITHUB_TOKEN` (contents:read default; write only where a job publishes); no secrets in PR runs from forks.

## 7. Vulnerability handling

Security issues: private report via GitHub security advisories (enabled Phase 1). Severity triage ≤ 72 h; patch releases out-of-band; CHANGELOG notes without exploit detail until users can update.
